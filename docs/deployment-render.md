## Key constraint and storage decision

A Render persistent disk is attached to exactly **one** service and cannot be read by any other service
(Render docs: "You can't access a service's disk from any other service"; Render suggests object storage
for sharing). The web service (uploads, downloads) and the receipt worker (reads files to send to the
provider) are separate services, so the local filesystem backend cannot be used.

**Recommendation: store private receipts and photos in the Render Postgres database**
(`PRIVATE_STORAGE_BACKEND=database`, `apps.core.storage.DatabaseStorage`, table `core_storedfile`).

- One durable store shared by web and worker over Render's private network; no extra vendor or credentials.
- Covered by the same Postgres point-in-time recovery and exports as the financial data (one backup story).
- Still private: no URLs; owner-checked views stream the bytes. Tested on SQLite and PostgreSQL, and in a
  production-like run (gunicorn, DEBUG off, database storage) in this sprint.
- Size: one user. Uploads ≤ 15 MB; iPhone photos are typically 1–4 MB (+ a JPEG preview for HEIC);
  project photos are re-encoded to ≤ 2400 px JPEG. Roughly 1 GB per ~300–500 receipts.
- Alternative if volume grows: an S3-compatible private bucket (e.g. Cloudflare R2/AWS S3) behind the same
  storage interface, with short-lived signed URLs issued only after the owner check. Not needed now.

## Access

- Login-only: every page except sign-in, `/healthz/` and the web manifest requires authentication
  (`LoginRequiredMiddleware`); no signup; no Django admin. HTTPS enforced (`DJANGO_HTTPS=1`: SSL redirect,
  HSTS, secure cookies; `/healthz/` exempt from the redirect for Render's internal check).
- Owner account (after first deploy), from the web service's Render **Shell**:
  `python manage.py create_owner alistair` (prompts for a password; validated; the account starts empty).
- Do **not** run `seed_demo` in production unless a separate demo account is wanted (it only touches
  accounts flagged `is_demo`).

## Worker restart and shutdown behaviour

- Deploys/maintenance: Render sends SIGTERM, waits the shutdown delay (configured 90 s), then SIGKILL.
  `process_receipts --watch` traps SIGTERM, finishes the current job and exits ("Stopped.").
- Crash or SIGKILL mid-reading: the job keeps its lease (180 s); after the worker restarts the job is
  re-claimed on expiry (attempt 2 of 2) or failed if attempts are used up. The newer attempt's claim token
  prevents a stale attempt overwriting it.
- Rehearsed locally in Sprint 2A (fake extractor, no paid calls): SIGTERM during an 8 s reading → job
  completed then clean stop; SIGKILL during a reading → restart left the leased job alone, then recovered
  it after lease expiry and applied the result on attempt 2. **Hosted supervisor behaviour is unverified
  until deployment.**

## Backups and restore

- Paid Render Postgres has point-in-time recovery (Hobby workspace: past 3 days) and dashboard logical
  exports retained 7 days. Because files live in the database, these cover receipts and photos too.
- Additionally (recommended): a weekly off-platform copy — download the dashboard export (or `pg_dump
  -Fc` from a trusted machine using the external connection string, temporarily allowing that IP) to the
  founder's encrypted storage. Render also documents automated backups to Amazon S3.
- Restore test before relying on it: restore an export into a new Render Postgres instance, point a
  temporary web service at it, sign in and open a receipt. Not yet performed (no infrastructure).
